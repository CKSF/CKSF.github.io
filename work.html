从信息断层到稳定发布

故事进度0%
01 · 起点

一个不在任务清单里的产品问题

刚加入团队时，我每天查看代码变化，发现开发者很清楚本周合入了什么，但最终用户和接入方几乎感知不到产品一直在进步。

它不是数据开发的主链路，却会削弱产品完整度，也让持续投入难以形成用户认知。我主动提出在默认入口展示近期变化和核心能力。

02 · MVP

先解决两个仓库之间的边界

数据和管理逻辑属于主应用，用户入口却位于另一个独立构建、独立发布的仓库。复制一套逻辑会增加维护成本，直接调用又会制造部署耦合。

我将用户入口设计成轻量展示容器，加载主应用提供的页面。这样两边职责清楚，也可以独立开发、部署和演进。

03 · 闭环

把人工周报变成可审核的流水线

跨仓展示打通后，我继续解决人工整理慢且容易遗漏的问题：CI 收集代码变化，AI 把技术差异改写成用户价值，再写入待审核草稿。

AI 不拥有发布权。开发者必须先比较、编辑和确认，内容才会进入数据库并展示给用户。这让效率和内容质量同时可控。

04 · 反馈

上线不是结束，38 条记录暴露了模型缺陷

上线初期运行正常，但一周后出现 38 条冗长、重复的更新。问题不在生成质量，而在我最初采用逐条追加的数据模型。

同一能力的多次修改被拆成多条记录，代码细节淹没了用户真正关心的能力变化。

05 · 重构

从提交记录转向每周产品快照

我重新设计状态模型：每周维护一份正式内容和一份待审核草稿，并记录展示与删除状态。

内容按“新能力”和“新增端侧支持”重新排序，审核页也改成类似代码差异的比较方式，让开发者更容易看懂和修改变化。

06 · 交付

补齐一条链路长期运行所需的能力

我继续处理 AI 输出异常、流水线失败和不同网络环境联调等问题，加入输出整理、明确日志、失败重试和测试部署流程。

最终交付的不只是一张页面，而是一条从发现产品问题、完成跨仓开发，到上线后根据真实反馈重构的完整工程闭环。

// DEVELOPMENT STORY

从版本选择到 Agent 能力边界

故事进度0%
01 · 需求

不同用户需要同一 Skill 的不同版本

个人可以维护自己的版本，团队需要共享版本，系统也会提供默认版本。它们可能同名，但适合的任务和维护者并不相同。

用户需要自由启停，也需要并排测试不同版本，而不是被系统永久绑定到单一实现。

02 · 原则

给 Agent 的能力必须必要且足够

把所有 Skill 都交给 Agent 看似功能丰富，实际会占用上下文，并增加误选能力的概率。

我们的目标是只提供完成当前任务所需、用户允许使用的版本，在能力完整和运行效率之间取得平衡。

03 · 模型

统一来源、版本、开关和优先级

我们将个人、协作空间和系统能力放入同一套状态规则。同名版本按明确顺序选择，当前版本关闭后再回退到下一可用版本。

用户看到的是可选择的版本，Agent 获得的是解析后的唯一结果，两者职责分开。

04 · 上线

真实文件并不总符合约定

上线后发现，一些 Skill 的目录名和文件中声明的名称并不一致；还有同名版本和路径写法不规范，导致解析冲突或能力消失。

我们继续补充名称解析兼容、同名消歧、异常提示和路径校验，让已有 Skill 不必全部重写也能稳定接入。

05 · 防线

不能只在页面上隐藏

如果只改变按钮，Agent 仍可能从能力加载、文件视图或旧会话选择中找到已关闭的 Skill。

因此三个运行入口都执行同一状态校验，确保关闭后的能力不可见、不可选、不可调用。

06 · 价值

把用户选择转化为 Agent 效率

用户获得了选择和比较不同版本的能力，也能为不同任务保留不同组合。

Agent 的上下文更精简，搜索范围更准确，错误调用更少；用户控制和运行效率由同一套机制同时保证。

07 · 稳定性

非核心控制不能拖住核心任务

一次线上问题暴露出开关信息成为会话必等项，局部阻塞被放大成整体不可用。

我们隔离非核心请求，补充超时与降级，并持续追踪异常根因，让控制能力失效时也不影响用户继续对话。

把跨端开发收进一个产品闭环

故事进度0%
01 · 产品问题

用户的任务完整，产品体验却是断开的

数据开发不是一个页面内的动作。用户会在数据集、查询、看板、实验和服务等端侧之间切换，反复搬运上下文和配置。

真正的问题不只是步骤多，而是当前产品只能回答一小段，无法陪用户完成整个开发任务。

02 · 产品目标

让用户不离开当前入口也能完成开发

我们希望 Agent 成为统一入口：理解目标、连接下游能力、检查执行条件，并把结果带回当前对话。

这意味着不能只做一个快捷表单，而要把多个端侧重新组织成连续、可完成的用户路径。

03 · 路径拆解

先从高频的数据集创建切入

我完整走查真实网页流程，记录每个请求、参数和依赖，区分哪些信息必须由用户决定，哪些可以由 Agent 自动获得。

用户只需提供最关键的表和项目，Agent 自动读取结构与可写目录，再让用户确认字段。

04 · 可信执行

让 Agent 真正做事，也让结果可控

创建前先进行 dry-run，集中检查数据源、字段、目录、权限和请求参数，避免错误进入正式执行。

校验通过后直接创建，并把结果链接送回对话。用户可以原地确认产物，而不是再去另一个产品中寻找。

05 · 完整闭环

一次创建不是流程终点

能力继续支持修改字段与指标、通过 SQL 创建，并衔接后续使用场景。

这样用户能在同一产品里持续完善数据产物，而不是完成第一步后又回到跨端操作。

06 · 能力扩展

从数据集扩展到更多开发任务

在数据集之外，我还参与实验工单和服务接入的开发与适配，让需求、配置、执行和结果逐步汇入同一入口。

数据集 Skill 上线次周成功调用量相对增长 +520%，证明用户开始采用这条完整路径处理真实工作。

07 · 平台适配

用户留在产品里，Skill 就要理解产品

通用 Skill 会自行获取权限和参数，但当前产品已经维护这些信息。重复获取会增加工具调用、推理轮次和失败点。

我将能力改为复用平台现有上下文，让执行更快、更稳定，也让跨端能力真正融入产品，而不是外挂在产品旁边。

From an Information Gap to Reliable Release

Story progress0%
01 · ORIGIN

A Product Problem Outside the Task List

When I joined, I followed code changes every day. Developers knew what shipped, but users and integration partners could barely see that the product kept improving.

It was outside the core data workflow, yet it weakened product completeness. I proposed using the default entry point to show recent changes and key capabilities.

02 · MVP

Define the Boundary Between Two Repositories

Data and management belonged to the main app, while the user entry point lived in a separately built and deployed repository. Copying logic would raise maintenance cost; direct coupling would tie deployments together.

I made the user entry point a lightweight display container for a page served by the main app. Each side kept a clear role and could evolve independently.

03 · LOOP

Turn Manual Notes into a Reviewed Pipeline

After the cross-repository display worked, I addressed slow and incomplete manual summaries. CI collects changes, AI translates technical differences into user value, and writes a review draft.

AI never receives publishing rights. A developer compares, edits, and approves the draft before it reaches the database and users.

04 · FEEDBACK

Thirty-eight Entries Exposed a Model Flaw

The first release looked healthy, but one week later it produced 38 long, repetitive updates. Generation quality was not the root cause; my append-only model was.

Repeated changes to one capability became separate records, and code-level detail buried the product changes users cared about.

05 · REBUILD

Move from Commit Records to a Weekly Product Snapshot

I redesigned the state model around one published version and one review draft per week, with display and deletion state.

Content was reordered around new capabilities and newly supported clients. The review page adopted a difference view so developers could understand and edit changes quickly.

06 · DELIVERY

Make the Whole Path Sustainable

I then handled malformed AI output, pipeline failures, and testing across network environments through cleanup, clear logs, retries, and deployment procedures.

The final delivery was not a page. It was a complete product-engineering loop from discovering the problem and crossing repository boundaries to rebuilding the system after real feedback.

// DEVELOPMENT STORY

From Version Choice to an Agent Capability Boundary

Story progress0%
01 · NEED

Different Users Need Different Versions of One Skill

Individuals can maintain their own version, teams share another, and the system provides a default. They may share a name while serving different tasks and owners.

Users need to enable and disable them freely and compare versions instead of being locked into one implementation.

02 · PRINCIPLE

Agent Context Must Be Sufficient and Necessary

Giving the agent every Skill looks powerful but consumes context and increases the chance of choosing the wrong capability.

Our goal was to provide enough to complete the task, but only from versions the user allowed.

03 · MODEL

Unify Source, Version, State, and Priority

User, workspace, and system capabilities follow one state model. Same-name versions resolve in a clear order and fall back when the active layer is disabled.

Users see choices, while the agent receives one resolved result. Those responsibilities stay separate.

04 · LAUNCH

Real Skill Files Do Not Always Follow Conventions

After launch, some folder names differed from names declared inside Skill files. Same-name versions and irregular paths caused conflicts or missing capabilities.

We added parsing compatibility, same-name disambiguation, clearer errors, and path validation so existing Skills could connect without a full rewrite.

05 · DEFENSE

Hiding a Button Is Not Enforcement

If only the UI changes, the agent can still find a disabled Skill during loading, through the file view, or from an older conversation selection.

All three runtime entry points enforce the same state so disabled capabilities are invisible, unselectable, and unreachable.

06 · VALUE

Turn User Choice into Agent Efficiency

// DEVELOPMENT STORY

Bring Cross-product Development into One Loop

Story progress0%
01 · PRODUCT PROBLEM

The User Task Was Whole, but the Experience Was Fragmented

Data development spans dataset, query, dashboard, experiment, and service products. Users moved context and configuration between them by hand.

The deeper problem was not form length. Our product could answer one part of the task but could not stay with users until the work was complete.

02 · PRODUCT GOAL

Complete Development Without Leaving the Entry Point

We wanted the agent to become one entry point that understands intent, connects downstream capabilities, checks conditions, and brings the result back.

This required redesigning separate products as one continuous user journey, not simply turning a form into chat.

03 · PATH DESIGN

Start with the High-frequency Dataset Workflow

I walked the real web flow and recorded each request, parameter, and dependency. I separated decisions only users could make from context the agent could discover.

Users provide the essential table and project. The agent reads schema and writable directories, then asks them to confirm fields.

04 · TRUSTED EXECUTION

Let the Agent Act While Keeping Results Controlled

A dry run checks the source, fields, directory, permissions, and request parameters before any formal action begins.

After validation, the Skill creates the asset and returns its link to the conversation. Users confirm the result without searching another product.

05 · COMPLETE LOOP

Initial Creation Is Not the End

The capability also supports later field and metric edits and SQL-based creation, then connects to downstream use.

Users can keep refining the data asset inside one product instead of returning to a fragmented multi-product workflow.

06 · EXPANSION

Grow from Datasets to More Development Tasks

I also contributed to experiment work orders and service integration, bringing requirements, setup, execution, and results toward the same entry point.

Successful dataset Skill calls grew 520% in week two, showing that users adopted this complete path for real work.

07 · ADAPTATION

To Keep Users in the Product, Skills Must Understand It

A generic Skill fetched permissions and parameters that the host product already maintained, adding calls, reasoning turns, and failure points.

I adapted it to reuse product context, making execution faster and more reliable while integrating downstream capability into the product itself.
